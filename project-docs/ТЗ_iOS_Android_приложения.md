# ТЗ для iOS и Android приложений: свадебный маркетплейс

Версия: 0.1  
Дата: 14 июля 2026  
Приоритет: mobile-first

## 1. Цель мобильных приложений

Разработать мобильные приложения для iOS и Android, через которые клиенты ищут свадебных подрядчиков, отправляют заявки, бронируют даты, сохраняют избранное и общаются с подрядчиками.

Для подрядчиков приложение должно стать рабочим кабинетом: профиль, услуги, портфолио, заявки, календарь, сообщения, отзывы и базовая аналитика.

Административную панель на первом этапе делать веб-интерфейсом. Мобильная админка не входит в MVP, если отдельно не будет утверждена.

## 2. Роль приложений в общей архитектуре

Приложения iOS и Android являются основным пользовательским интерфейсом.

Web/Bitrix часть используется для:

- административной панели;
- управления каталогом и контентом;
- SEO-витрины;
- хранения и модерации данных;
- backend/API для мобильных приложений;
- интеграций;
- аналитики;
- обработки уведомлений.

Мобильные приложения не должны напрямую работать с базой данных Bitrix. Все операции идут через API.

## 3. Формат разработки

Рекомендуемый подход для MVP: одно кроссплатформенное приложение для iOS и Android с двумя ролями внутри: клиент и подрядчик.

Причины:

- быстрее запуск;
- единая логика;
- ниже стоимость поддержки;
- один дизайн-сценарий;
- проще развивать чат, уведомления и заявки.

Альтернативы:

- два отдельных приложения: "для клиентов" и "для подрядчиков";
- полностью нативная разработка iOS и Android;
- webview-гибрид на базе сайта.

Рекомендация: не делать MVP как простую webview-обертку сайта. Для маркетплейса важны нативные сценарии: пуши, быстрый поиск, избранное, загрузка фото, календарь, чат и глубокие ссылки.

Финальный стек разработки нужно выбрать на этапе технического проектирования.

## 4. Пользовательские роли в приложении

### 4.1. Клиент

Клиент использует приложение для:

- поиска подрядчиков;
- фильтрации и сравнения;
- просмотра карточек;
- сохранения избранного;
- сохранения поисков;
- отправки заявок;
- запроса брони даты;
- переписки;
- отзывов;
- чек-листа подготовки;
- калькулятора бюджета;
- подбора подрядчиков.

### 4.2. Подрядчик

Подрядчик использует приложение для:

- регистрации;
- заполнения профиля;
- добавления услуг;
- загрузки портфолио;
- отправки карточки на модерацию;
- обработки заявок;
- управления календарем;
- переписки с клиентами;
- просмотра отзывов;
- просмотра аналитики;
- настройки уведомлений.

### 4.3. Администратор

Администратор работает через веб-админку.

В мобильном MVP администраторские функции не реализуются, кроме возможного просмотра статусов через веб.

## 7. Onboarding и регистрация

### 7.1. Первый запуск

Экран первого запуска:

- короткое позиционирование сервиса;
- выбор города;
- выбор роли: клиент / подрядчик;
- вход или регистрация;
- возможность пропустить регистрацию для просмотра каталога.

### 7.2. Регистрация клиента

Минимальные поля:

- имя;
- телефон или email;
- пароль или вход по коду;
- город;
- согласие на обработку персональных данных.

### 7.3. Регистрация подрядчика

Минимальные поля:

- имя или название компании;
- категория;
- город;
- телефон;
- email;
- пароль или вход по коду;
- согласие на обработку персональных данных;
- согласие с правилами размещения.

После регистрации подрядчик попадает в мастер заполнения профиля.

## 8. Главная клиента

Цель: быстро привести клиента к поиску подрядчика.

Блоки:

- поисковая строка;
- выбор города;
- быстрые категории;
- подбор по дате и бюджету;
- популярные категории;
- лучшие специалисты;
- новые подрядчики;
- рекомендации;
- статьи/советы;
- быстрый вход в чек-лист и калькулятор.

Требования:

- главный поиск виден в первом экране;
- категории доступны без длинного скролла;
- CTA должны быть понятны без инструкции;
- блоки управляются из backend/админки;
- на слабом интернете главный экран не должен быть пустым.

## 9. Каталог и поиск

Функции:

- список подрядчиков;
- поиск по названию, категории, городу;
- фильтры;
- сортировки;
- избранное из списка;
- переход в карточку;
- пагинация или бесконечная подгрузка;
- скелетоны загрузки;
- пустые состояния.

Фильтры:

- город;
- категория;
- цена от/до;
- дата свадьбы;
- рейтинг;
- опыт;
- тип услуги;
- количество гостей;
- стиль свадьбы;
- отметка "проверен";
- доступен на выбранную дату.

Сортировки:

- по умолчанию;
- рейтинг;
- цена;
- новые.

Критерий готовности: пользователь может найти подрядчика за 2-3 действия после открытия приложения.

## 10. Карточка подрядчика

Обязательные блоки:

- фото/логотип;
- имя или компания;
- категория;
- город;
- отметка "проверен";
- рейтинг;
- опыт;
- количество свадеб;
- описание;
- услуги и пакеты;
- портфолио;
- отзывы;
- доступность по датам;
- похожие подрядчики;
- жалоба.

CTA:

- написать;
- оставить заявку;
- забронировать дату;
- позвонить;
- WhatsApp;
- добавить в избранное;
- поделиться.

Требования:

- основной CTA закреплен в нижней части экрана;
- телефон и WhatsApp логируются как действия;
- длинные описания сворачиваются;
- портфолио открывается полноэкранно;
- отзывы можно фильтровать или сортировать после MVP.

## 11. Заявки

### 11.1. Создание заявки клиентом

Заявка создается из:

- карточки подрядчика;
- услуги;
- подбора;
- калькулятора;
- чата.

Поля:

- дата свадьбы;
- город;
- количество гостей;
- бюджет;
- комментарий;
- выбранная услуга;
- контактные данные.

Требования:

- форма должна быть короткой;
- часть данных подставляется из профиля;
- после отправки пользователь видит статус;
- заявка появляется в кабинете клиента и подрядчика;
- подрядчик получает уведомление.

### 11.2. Заявки клиента

Клиент видит:

- список заявок;
- статусы;
- подрядчика;
- дату;
- последние сообщения;
- действия: открыть, написать, отменить.

### 11.3. Заявки подрядчика

Подрядчик видит:

- новые заявки;
- статус;
- данные клиента;
- дату события;
- бюджет;
- комментарий;
- действия: принять в работу, ответить, подтвердить, отклонить.

## 12. Бронирование и календарь

### 12.1. Клиент

Клиент может:

- выбрать дату;
- увидеть доступность подрядчика;
- отправить запрос на бронь;
- получить подтверждение или отклонение;
- открыть бронь из своих заявок.

### 12.2. Подрядчик

Подрядчик может:

- отмечать занятые даты;
- видеть запросы на бронь;
- подтверждать или отклонять запросы;
- видеть календарь занятости.

Правило: система не позволяет подтвердить две брони на одну дату для одного подрядчика.

## 13. Чат и сообщения

Чат нужен как переписка клиента и подрядчика в контексте заявки или карточки.

MVP-функции:

- список диалогов;
- экран диалога;
- текстовые сообщения;
- статусы отправки/прочтения;
- push о новом сообщении;
- история сообщений;
- привязка к заявке;
- жалоба на сообщение.

После MVP:

- вложения;
- быстрые ответы;
- шаблоны ответов подрядчика;
- медиа;
- интеграция с Bitrix24 CRM, если подтверждена.

Важно: архитектуру чата нужно выбрать отдельно. Не закладывать чат как простое включение устаревшего веб-мессенджера Bitrix.

## 14. Кабинет подрядчика

### 14.1. Профиль

Подрядчик редактирует:

- имя или компанию;
- категорию;
- город;
- описание;
- опыт;
- количество свадеб;
- контакты;
- соцсети;
- фото/логотип;
- документы для верификации, если функция включена.

### 14.2. Услуги

Подрядчик может:

- создать услугу;
- редактировать услугу;
- скрыть услугу;
- отправить на модерацию;
- видеть статус модерации;
- видеть причину отклонения.

### 14.3. Портфолио

Подрядчик может:

- загрузить фото;
- добавить видео-ссылки;
- создать кейс;
- менять порядок;
- отправить на модерацию.

### 14.4. Аналитика

Показывать:

- просмотры карточки;
- клики по телефону;
- клики по WhatsApp;
- заявки;
- бронирования;
- добавления в избранное;
- просмотры портфолио.

## 15. Избранное и сохраненные поиски

Клиент может:

- добавить подрядчика в избранное;
- удалить из избранного;
- открыть избранное с нижнего меню;
- сохранить набор фильтров;
- назвать сохраненный поиск;
- получать уведомления о новых подрядчиках по сохраненному поиску.

## 16. Отзывы

Клиент может оставить отзыв только после подтвержденной брони или закрытой заявки.

Функции:

- рейтинг;
- текст;
- публикация после проверки правил;
- жалоба на отзыв;
- отображение в карточке.

Подрядчик видит отзывы в своем кабинете.

Администратор модерирует отзывы через веб-админку.

## 17. Калькулятор свадьбы

Функции:

- ввод города;
- ввод количества гостей;
- выбор стиля свадьбы;
- расчет примерного бюджета;
- разбивка по категориям;
- сохранение результата;
- прикрепление результата к заявке.

Условие: формулы и диапазоны цен предоставляет владелец продукта.

## 18. Чек-лист

Функции:

- дата свадьбы;
- шаблон задач;
- расчет дедлайнов от даты свадьбы;
- отметка выполнения;
- добавление своих задач;
- уведомления о важных сроках;
- сохранение прогресса.

## 19. Подбор подрядчиков

MVP: подбор по правилам.

Ввод:

- город;
- дата;
- стиль;
- бюджет;
- категория;
- рейтинг;
- доступность.

Вывод:

- список подрядчиков;
- объяснение, почему подрядчик подходит;
- сохранение подборки;
- создание заявки.

## 20. Push-уведомления

Обязательные push-события:

- новая заявка подрядчику;
- изменение статуса заявки клиенту;
- запрос брони подрядчику;
- подтверждение/отклонение брони клиенту;
- новое сообщение;
- результат модерации подрядчику;
- новый отзыв подрядчику;
- напоминание по чек-листу;
- новая карточка по сохраненному поиску, если включено.

Требования:

- пользователь может включить/выключить типы уведомлений;
- уведомление открывает нужный экран приложения;
- критичные события дублируются в личном кабинете.

## 21. Deep links

Нужно предусмотреть ссылки на:

- карточку подрядчика;
- заявку;
- бронь;
- диалог;
- подборку;
- статью;
- приглашение в приложение.

Deep links нужны для пушей, email, мессенджеров и рекламных кампаний.

- авторизации;

- ролей;
- городов;
- категорий;
- стилей;
- каталога;
- поиска;
- фильтров;
- карточки подрядчика;
- избранного;
- сохраненных поисков;
- заявок;
- бронирований;
- сообщений;
- отзывов;
- календаря;
- загрузки фото;
- уведомлений;
- аналитики;
- калькулятора;
- чек-листа;
- подбора;
- жалоб.

API должен возвращать данные в формате, удобном для мобильных экранов: без лишних тяжелых полей, с пагинацией, статусами и предсказуемыми ошибками.

## 23. Состояния интерфейса

Для каждого ключевого экрана нужны состояния:

- загрузка;
- пусто;
- ошибка сети;
- нет результатов;
- нет доступа;
- успех действия;
- ошибка валидации;
- требуется авторизация;
- ожидает модерации.

Приложение не должно показывать пустой белый экран при медленном интернете.

## 24. Offline и слабый интернет

MVP-требования:

- корректные ошибки сети;
- повтор действия после восстановления сети;
- кэш последнего открытого каталога;
- кэш избранного;
- кэш профиля;
- запрет критичных действий без сети с понятным сообщением.

После MVP:

- очередь отправки сообщений;
- offline-черновики заявок;
- offline-черновики услуг подрядчика.

## 25. Аналитика приложения

Нужно логировать:

- установку;
- регистрацию;
- выбор роли;
- выбор города;
- поиск;
- применение фильтров;
- открытие карточки;
- добавление в избранное;
- отправку заявки;
- запрос брони;
- отправку сообщения;
- клики по телефону;
- клики по WhatsApp;
- расчет бюджета;
- создание чек-листа;
- сохранение подбора.

Аналитика должна позволять смотреть конверсию:

- открытие приложения -> поиск;
- поиск -> карточка;
- карточка -> заявка;
- карточка -> звонок/WhatsApp;
- заявка -> бронь;
- подрядчик получил заявку -> ответил.

## 30. Критерии готовности MVP

MVP приложений готов, если:

- приложение запускается на iOS и Android;
- пользователь может зарегистрироваться;
- пользователь может выбрать роль;
- клиент может найти подрядчика через поиск и фильтры;
- клиент может открыть карточку;
- клиент может добавить подрядчика в избранное;
- клиент может отправить заявку;
- подрядчик получает заявку;
- подрядчик может создать профиль;
- подрядчик может создать услугу;
- подрядчик видит статус модерации;
- клиент и подрядчик могут обменяться сообщениями, если чат входит в MVP;
- работают push-уведомления по заявкам и сообщениям;
- можно запросить или отметить бронь;
- нельзя подтвердить две брони на одну дату для одного подрядчика;
- основные события логируются в аналитику;
- приложение корректно обрабатывает отсутствие сети;
- есть privacy policy и terms для публикации;
- сборки проходят тестирование на реальных устройствах.
