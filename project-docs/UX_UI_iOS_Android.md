# UX/UI ТЗ: iOS и Android приложения свадебного маркетплейса

Версия: 0.1  
Дата: 14 июля 2026  
Фокус: mobile-first

## 1. UX-принцип

Приложение должно помогать пользователю быстро перейти от намерения "мне нужен подрядчик на свадьбу" к конкретному действию: заявке, звонку, WhatsApp, брони или сохранению.

Ключевая логика интерфейса:

- поиск должен быть заметен сразу;
- фильтры должны быть простыми и быстрыми;
- карточка должна быстро отвечать на вопросы: кто, где, сколько стоит, есть ли доверие, как связаться;
- заявка должна быть короткой;
- подрядчик должен видеть новые обращения без лишних переходов;
- все важные действия должны работать на мобильном одной рукой.

## 2. Главные пользовательские сценарии

### 2.1. Клиент ищет подрядчика

1. Открывает приложение.
2. Выбирает город.
3. Вводит запрос или выбирает категорию.
4. Применяет фильтры.
5. Смотрит список.
6. Открывает карточку.
7. Сохраняет, звонит, пишет, бронирует или отправляет заявку.

### 2.2. Клиент сохраняет подбор

1. Настраивает фильтры.
2. Сохраняет поиск.
3. Возвращается к нему из профиля.
4. Получает уведомления о новых подходящих подрядчиках, если включено.

### 2.3. Клиент отправляет заявку

1. Нажимает "Оставить заявку".
2. Указывает дату, гостей, бюджет и комментарий.
3. Проверяет контакты.
4. Отправляет.
5. Видит статус заявки.
6. Получает ответ в приложении.

### 2.4. Подрядчик обрабатывает заявку

1. Получает push.
2. Открывает входящую заявку.
3. Видит дату, бюджет, комментарий и клиента.
4. Отвечает в чате.
5. Меняет статус заявки.
6. Подтверждает или отклоняет бронь.

### 2.5. Подрядчик создает карточку

1. Регистрируется как подрядчик.
2. Заполняет профиль.
3. Добавляет услугу.
4. Загружает портфолио.
5. Отправляет на модерацию.
6. Видит статус и причину отклонения, если есть.

## 5. Главная клиента

Первый экран:

- город;
- поисковая строка;
- быстрые категории;
- CTA к подбору подрядчиков;
- вход в калькулятор или чек-лист.

Ниже:

- популярные категории;
- лучшие специалисты;
- новые подрядчики;
- рекомендации;
- статьи и советы.

UX-требования:

- поиск расположен в верхней части;
- категории видны без длинного скролла;
- карточки подрядчиков компактные;
- загрузка идет через skeleton-элементы;
- если город не выбран, приложение просит выбрать город.

## 6. Каталог

Карточка в списке должна показывать:

- фото;
- имя/компанию;
- категорию;
- город;
- рейтинг;
- цену или "от";
- отметку "проверен";
- быстрый лайк/избранное;
- доступность на дату, если дата выбрана.

Верх каталога:

- строка поиска;
- выбранный город;
- кнопка фильтров;
- сортировка;
- количество результатов.

Состояния:

- загрузка;
- нет результатов;
- ошибка сети;
- результаты устарели;
- требуется выбрать город.

## 7. Фильтры

Фильтры открываются как отдельный экран или bottom sheet.

Поля:

- город;
- категория;
- цена от/до;
- дата свадьбы;
- рейтинг;
- опыт;
- тип услуги;
- количество гостей;
- стиль;
- только проверенные;
- доступен на дату.

UX-требования:

- кнопка "Показать результаты" закреплена снизу;
- есть кнопка "Сбросить";
- выбранные фильтры видны как чипы;
- после применения пользователь возвращается в каталог;
- фильтры не должны быть перегружены на первом экране.

## 8. Карточка подрядчика

Структура сверху вниз:

1. Фото/обложка.
2. Имя или компания.
3. Категория, город, рейтинг, проверка.
4. Основные CTA.
5. Цены/пакеты.
6. Описание.
7. Портфолио.
8. Календарь/доступность.
9. Отзывы.
10. Похожие подрядчики.
11. Жалоба.

Закрепленная нижняя зона:

- основной CTA: "Оставить заявку" или "Написать";
- вторичные действия: телефон, WhatsApp, избранное.

UX-требования:

- ключевые действия доступны без прокрутки до конца;
- длинное описание сворачивается;
- портфолио открывается полноэкранно;
- цена видна до отправки заявки;
- если нет цены, показывать "Цена по запросу";
- если подрядчик не опубликован или скрыт, карточка недоступна клиенту.

## 9. Форма заявки

Поля:

- дата свадьбы;
- количество гостей;
- бюджет;
- комментарий;
- контактные данные;
- выбранная услуга.

UX-требования:

- форма короткая;
- данные из профиля подставляются автоматически;
- ошибки показываются рядом с полем;
- после отправки показывается экран успеха;
- пользователь может сразу открыть диалог.

## 10. Заявки клиента

Список заявок:

- подрядчик;
- дата;
- статус;
- последнее обновление;
- последнее сообщение;
- быстрый переход в диалог.

Деталка заявки:

- данные заявки;
- статус;
- история изменений;
- бронь;
- диалог;
- действия: написать, отменить.

## 11. Главная подрядчика

Первый экран подрядчика:

- новые заявки;
- ближайшие брони;
- непрочитанные сообщения;
- статус профиля;
- быстрые действия: добавить услугу, открыть календарь, открыть аналитику.

UX-требования:

- новые заявки должны быть заметнее статистики;
- проблемы модерации показывать явно;
- если профиль не заполнен, вести в мастер заполнения.

## 12. Создание профиля подрядчика

Лучший формат: пошаговый мастер.

Шаги:

1. Основные данные.
2. Категория и город.
3. Описание и опыт.
4. Контакты и соцсети.
5. Фото/логотип.
6. Услуга.
7. Портфолио.
8. Отправка на модерацию.

UX-требования:

- показывать прогресс;
- сохранять черновик;
- объяснять обязательные поля;
- после отправки показывать статус модерации.

## 13. Создание услуги

Поля:

- название;
- категория;
- цена;
- тип цены;
- состав пакета;
- условия;
- доп. услуги;
- медиа.

UX-требования:

- цена не должна быть обязательной, если выбран тип "по запросу";
- длинные поля вводятся на отдельных шагах;
- медиа можно добавить позже;
- без обязательных полей нельзя отправить на модерацию.

## 14. Календарь подрядчика

Состояния дат:

- свободно;
- занято;
- ожидает подтверждения.

UX-требования:

- подрядчик быстро отмечает дату как занятую;
- запросы на бронь выделяются отдельно;
- конфликт брони показывается явно;
- подтверждение брони требует явного действия.

## 15. Чат

Список диалогов:

- имя клиента/подрядчика;
- последняя фраза;
- дата;
- статус прочтения;
- привязка к заявке.

Экран диалога:

- сообщения;
- поле ввода;
- статус отправки;
- ссылка на заявку;
- жалоба;
- быстрые действия.

UX-требования:

- отправка не должна теряться при слабом интернете;
- ошибки отправки показываются рядом с сообщением;
- push открывает нужный диалог;
- если чат недоступен, показывать понятное состояние.

## 16. Избранное

Экран избранного:

- список сохраненных подрядчиков;
- быстрый фильтр по категории;
- переход в карточку;
- удаление из избранного;
- состояние, если карточка скрыта или недоступна.

## 17. Чек-лист

Экран:

- дата свадьбы;
- список задач;
- дедлайны;
- статус выполнения;
- добавить задачу;
- фильтр: все / активные / выполненные.

UX-требования:

- прогресс должен быть виден;
- задачи группируются по срокам;
- напоминания не должны быть навязчивыми.

## 18. Калькулятор

Шаги:

1. Город.
2. Количество гостей.
3. Стиль свадьбы.
4. Дополнительные параметры.
5. Результат.

Результат:

- общий диапазон бюджета;
- разбивка по категориям;
- сохранить расчет;
- создать заявку или подбор.

## 19. Подбор подрядчиков

Шаги:

1. Город.
2. Дата.
3. Стиль.
4. Бюджет.
5. Категории.
6. Результат.

Карточка результата:

- подрядчик;
- почему подходит;
- цена;
- рейтинг;
- доступность;
- CTA.

## 20. Состояния интерфейса

Для каждого важного экрана дизайнер должен подготовить:

- default;
- loading;
- empty;
- error;
- no internet;
- unauthorized;
- success;
- validation error;
- moderation pending;
- blocked/hidden.

## 22. Адаптация iOS и Android

Общие требования:

- соблюдать привычные паттерны платформ;
- корректно работать с safe area;
- учитывать разные размеры экранов;
- не прятать CTA под системные жесты;
- поддерживать темный режим только если он утвержден отдельно;
- использовать системные permission-экраны аккуратно.

Разрешения:

- уведомления;
- фото/медиа;
- камера;
- геолокация, если будет использоваться.

## 23. Тексты интерфейса

Нужны короткие тексты для:

- ошибок;
- пустых состояний;
- модерации;
- статусов заявок;
- статусов брони;
- согласий;
- пушей;
- подсказок при заполнении профиля.

Тон: спокойный, понятный, без технических формулировок.

## 25. Критерии готовности UX/UI

UX/UI можно передавать в разработку, если:

- есть карта экранов;
- описаны клиентские и подрядчикские сценарии;
- есть mobile wireframes;
- есть дизайн ключевых экранов;
- есть UI-kit;
- есть состояния экранов;
- есть адаптация под iOS и Android;
- описаны ошибки и пустые состояния;
- описаны пуши и deep links;
- макеты покрывают MVP;
- разработчик понимает все переходы между экранами.
